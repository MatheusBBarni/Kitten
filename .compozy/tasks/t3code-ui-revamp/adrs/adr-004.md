# ADR-004: Persist immutable review evidence and page diffs per file

## Status

Accepted

## Date

2026-07-26

## Context

The current review command validates card identity, version, and `ready_for_review` state but does not prove which bytes the operator reviewed. Reading the live worktree on demand cannot reproduce an earlier review after later mutations. Returning a complete patch inside the card projection would also create large RPC payloads and make ordinary inspector refreshes scale with diff size.

## Decision

Capture immutable review evidence before committing a card to `ready_for_review`.

The host stores:

- an immutable evidence manifest bound to board, card, attempt, generation, worktree binding, base commit, head commit, dirty/untracked policy, creation time, and canonical evidence digest;
- one immutable file record per changed path with status, old/new path, mode, text/binary classification, byte length, content digest, additions/deletions, and canonical per-file patch bytes when reviewable;
- a journal reference to the evidence identity and digest associated with the `ready_for_review` transition.

Canonical evidence includes tracked changes and eligible untracked regular files in stable path order. Binary entries bind byte digests without exposing binary content as text. Unsupported, unsafe, or oversized evidence keeps review unavailable.

RPC remains projection-only:

- `getReviewManifest` returns bounded metadata and review availability;
- `getReviewDiffChunk` returns one file's canonical patch in chunks of at most 64 KiB with offset, next offset, completion, binary, and too-large states;
- `reviewCard` and `submitCardPrompt` with `source: "request_changes"` require evidence identity, evidence digest, attempt identity, worktree binding identity, and expected card version.

Before any disposition, the host recomputes the current worktree evidence digest and compares it with the stored digest. Mismatch, missing evidence, unsafe files, or incomplete capture fails closed.

V1 limits are explicit and testable:

- at most 2,000 changed files;
- at most 8 MiB of canonical patch bytes per text file;
- at most 64 MiB of canonical patch bytes per evidence set;
- at most 64 KiB returned by one diff-chunk response.

Exceeding a limit produces a typed unavailable reason and disables disposition.

## Alternatives Considered

### Alternative 1: Store only Git identities and regenerate diffs

- **Description**: Persist base/head/worktree identities and recreate the patch whenever review opens.
- **Pros**: Smaller storage footprint.
- **Cons**: Dirty and untracked worktree content can disappear or change, preventing exact reproduction.
- **Why rejected**: It cannot guarantee that the bytes later approved match the bytes originally shown.

### Alternative 2: Read the live worktree only

- **Description**: Generate every diff directly from current worktree state without an immutable evidence artifact.
- **Pros**: Minimal schema and capture logic.
- **Cons**: Review becomes a moving target and cannot be audited or replayed.
- **Why rejected**: It violates the evidence-bound release gate.

### Alternative 3: Return the complete patch with the inspector

- **Description**: Embed all diff content in the normal card-inspector projection.
- **Pros**: Simple renderer API.
- **Cons**: Large payloads, repeated transfer, poor incremental rendering, and unnecessary content exposure.
- **Why rejected**: Manifest-first, per-file chunking preserves the plain-JSON boundary with bounded payloads.

## Consequences

### Positive

- Every accepted disposition refers to reproducible evidence.
- Review remains valid across renderer refresh and application restart.
- Ordinary Work Inbox and inspector queries stay small.
- Large, binary, stale, or unsafe evidence has explicit fail-closed behavior.

### Negative

- Review evidence adds immutable local storage.
- Final-stage completion must capture and validate evidence before `ready_for_review`.
- Large reviews can be unavailable in V1.
- Review services must handle Git race detection and evidence cleanup policy.

### Risks

- The worktree can mutate during capture. Verify state before and after capture and refuse the transition when they differ.
- Canonicalization bugs could produce unstable digests. Use byte-level golden fixtures covering rename, deletion, mode change, binary, untracked, whitespace, and path-order cases.
- Evidence can consume disk space. Retain it with the card's review history and expose diagnostics before introducing automatic deletion.

## Implementation Notes

- Add schema and services inside `packages/desktop`; do not expose filesystem handles, Git objects, or raw host errors over RPC.
- Store content bytes outside journal payload JSON while journaling immutable evidence identity and digest.
- Use typed content-minimized rejection codes for stale, missing, unsafe, binary-only, and oversized evidence.
