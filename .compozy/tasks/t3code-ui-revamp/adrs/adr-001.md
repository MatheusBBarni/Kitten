# ADR-001: Adopt a T3 Code-inspired supervision loop without replacing Kitten's workflow model

## Status

Accepted

## Date

2026-07-26

## Context

Kitten's desktop already owns repositories, boards, stages, cards, immutable attempts, attention states, review states, card-owned worktrees, and local host projections. Its current interface exposes those capabilities across a project sidebar, Kanban canvas, large card drawer, metadata-forward attempt history, persistent composer, and separate Settings surface.

T3 Code demonstrates a clearer daily interaction model for supervising concurrent agent work: a repository-grouped work inbox, one focused conversation, contextual changed-file review, compact action chrome, persistent input, and keyboard navigation. Copying its session identity, lifecycle, architecture, or full tool surface would conflict with Kitten's durable Kanban model and local-first authority.

The V1 decision must improve the complete repository-to-review loop without turning a UI revamp into a second workflow system or an unbounded desktop IDE project.

## Decision

Adopt T3 Code's interaction vocabulary as a thin but end-to-end Kitten supervision loop:

1. Present repository- and board-scoped navigation with visible counts and states for running, needs-attention, failed, and ready-for-review work.
2. Keep the Kanban canvas as the primary workspace while opening a selected card in a stable, dockable workbench on desktop and a focused sheet on narrow layouts.
3. Present the current attempt as a readable conversation with tool activity and Run Context available through progressive disclosure; keep older immutable attempts collapsed but accessible.
4. Keep a lightweight persistent composer attached to the selected card, with direct Enter submission, Shift+Enter newline behavior, explicit unavailable or blocked states, and existing stage, profile, model, and attention constraints.
5. Attach changed-file summaries to the relevant attempt and provide a focused review surface leading to approve or request-changes actions.
6. Permit a state-changing review action only when the host freshly validates a deterministic change-set identity bound to the relevant card, attempt, worktree, base, head, dirty and untracked-file policy, and digest. Fail closed when that evidence is stale or incomplete.
7. Bring Settings into normal application navigation and add visible, context-aware shortcuts for the critical supervision path.
8. Refresh Kitten's existing semantic design tokens toward T3 Code's quiet near-black hierarchy, restrained borders, sparse primary accent, semantic status colors, compact chrome, and selective emphasis around the composer.

Kitten retains its repository, board, stage, card, attempt, attention, and review identities. Host-owned SQLite projections, filesystem and Git authority, card-owned worktrees, typed plain-JSON RPC, stale-projection rejection, and local-first boundaries remain authoritative.

## Alternatives Considered

### Alternative 1: Full T3 Code feature and layout parity

- **Description**: Reproduce T3 Code's threads, session lifecycle, customizable panes, terminal, browser, file explorer, rich composer, and desktop interaction model.
- **Pros**: High visual and functional familiarity; broad desktop capability.
- **Cons**: Introduces competing identities and lifecycle semantics, expands privileged surfaces, and converts the revamp into an architectural rewrite.
- **Why rejected**: It obscures Kitten's differentiated governed workflow and delays validation of the core supervision loop.

### Alternative 2: Visual reskin only

- **Description**: Apply T3 Code-inspired colors, typography, spacing, borders, and component styling without changing navigation or review usage.
- **Pros**: Smaller and faster; low domain risk.
- **Cons**: Leaves cross-project triage, card focus, transcript hierarchy, and review fragmentation intact.
- **Why rejected**: It improves appearance without achieving the user's primary speed and context-preservation outcome.

### Alternative 3: Read-only supervisory spine

- **Description**: Add actionable navigation and a changed-files viewer but route review decisions outside the focused workspace.
- **Pros**: Reduces the first delivery slice and avoids premature review authority.
- **Cons**: Preserves context switching and leaves the repository-to-review loop incomplete.
- **Why rejected**: The complete loop is the product hypothesis. Review actions belong in V1 once deterministic diff provenance is proven; until then they must fail closed rather than move elsewhere.

## Consequences

### Positive

- The revamp produces a measurable workflow improvement instead of cosmetic parity.
- Developers retain board context while inspecting, steering, and reviewing a card.
- Cross-project attention and review work becomes visible without weakening stage authority.
- Review decisions gain explicit, reproducible evidence.
- The UI can evolve incrementally over stable Kitten-owned projections and identities.

### Negative

- V1 spans multiple connected surfaces and requires disciplined interaction-state design.
- Deterministic change-set provenance adds scope before approve or request-changes can be enabled.
- Visual similarity to T3 Code will be intentionally incomplete because Kitten retains the Kanban canvas and narrower tool surface.
- Current project, inspector, transcript, Settings, and responsive navigation patterns will need coordinated migration.

### Risks

- **Parallel UI state model**: status badges or inbox ordering could diverge from cards and stages. Mitigate with one host-owned canonical supervision projection.
- **False review evidence**: a displayed diff could drift from the approved bytes. Mitigate with fresh host validation, explicit Git identities, digest binding, and fail-closed commands.
- **Scope creep**: terminal, browser, file explorer, pane grids, and rich input could enter V1. Mitigate through explicit exclusions and KPI-gated follow-on work.
- **Keyboard conflicts**: global shortcuts could interfere with composer input. Mitigate with centralized context-aware commands and visible focus behavior.
- **Responsive regression**: stacking navigation above the Kanban could make the board unusable. Mitigate with off-canvas navigation and a focused narrow-screen workbench.

## Implementation Notes

- Deliver the supervision loop in integrated slices, but treat projection and command boundaries as durable production contracts.
- Keep filesystem handles, Git objects, SQLite handles, ACP connections, worktree paths requiring privilege, and secrets out of renderer projections.
- Instrument only content-free navigation, action, latency, and completion outcomes needed to evaluate the KPIs.
- Preserve native visual verification as a separate acceptance gate from automated component and contract tests.
