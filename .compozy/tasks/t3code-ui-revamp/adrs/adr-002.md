# ADR-002: Prioritize blocked work and require evidence-bound review

## Status

Accepted

## Date

2026-07-26

## Context

The desktop supervision loop must help an individual developer decide where to intervene across several repositories. Multiple states can demand attention at the same time: a live attempt may be blocked on user input, another card may be ready for review, and other work may have failed or still be running.

The review experience also introduces a consequential decision boundary. An approval can complete a card, while a request for changes must return work to the agent without losing the card, stage, conversation, or review context. The product must not encourage a reviewer to act on incomplete evidence or send a change request they did not explicitly approve.

## Decision

The cross-project Work Inbox prioritizes human action in this default order:

1. `needs_attention`
2. `ready_for_review`
3. failed work
4. running work
5. other settled work

Blocked live work appears first because it cannot progress without the developer. Within each group, the interface preserves repository and board context and uses a stable, predictable ordering rather than AI-generated priority.

Review controls follow these rules:

- Approve and Request changes remain unavailable until Kitten can present trustworthy, current evidence for the exact change set under review.
- Trustworthy review evidence is a non-negotiable V1 release gate. A stale or incomplete review must fail closed rather than offer a warning-only path.
- Selecting Request changes opens an editable, prefilled composer draft. It does not send a message or change the card state.
- The reviewer may edit or discard the draft. Enter sends the reviewer-approved message, while Shift+Enter inserts a newline.
- After the change request is successfully sent, the same card returns to active work in its current workflow stage and starts a new attempt. Kitten does not create a separate follow-up card.
- Approving trustworthy evidence completes the existing card through the established human review boundary.

## Alternatives Considered

### Alternative 1: Prioritize ready-for-review work

- **Description**: Place cards closest to completion above blocked active work.
- **Pros**: Encourages throughput and shortens the path from finished agent work to completion.
- **Cons**: Leaves live attempts idle while waiting for an answer and can increase the developer's mental ledger of blocked work.
- **Why rejected**: Kitten's primary V1 value is active supervision. Work that cannot progress without the user deserves the first intervention slot.

### Alternative 2: Require users to configure inbox ordering

- **Description**: Let each user decide how attention, review, failure, and running states are ordered.
- **Pros**: Supports different personal priorities.
- **Cons**: Adds setup and preference complexity before the product has validated the basic supervision loop.
- **Why rejected**: V1 needs a useful default and measurable behavior. Custom ordering can follow observed demand.

### Alternative 3: Send a fixed change request immediately

- **Description**: Make Request changes an immediate state-changing action with a standard agent message.
- **Pros**: Reduces interaction count and resumes work quickly.
- **Cons**: Removes the reviewer's opportunity to explain the required correction and risks accidental or context-poor dispatch.
- **Why rejected**: Explicit, editable human intent is more important than saving one interaction at the review boundary.

## Consequences

### Positive

- Blocked active work becomes the clearest intervention priority.
- Review remains a trustworthy human decision rather than a warning-backed shortcut.
- Change requests preserve card, stage, history, and repository context.
- Nothing is sent merely because the reviewer selected an action.
- The default ordering remains predictable and measurable.

### Negative

- Ready-for-review work may wait behind blocked active attempts.
- Review actions cannot ship before trustworthy evidence is available.
- Request changes requires an explicit edit-and-send step.
- Custom inbox ordering is deferred.

### Risks

- **Attention overload**: many blocked cards could crowd out review work. Mitigate with visible state groups, counts, and direct access to the review group.
- **Review bottleneck**: fail-closed evidence may temporarily make cards non-actionable. Mitigate with clear explanations of missing or stale evidence and a refresh path.
- **Accidental dispatch**: Enter inside a prefilled draft could send before the reviewer finishes editing. Mitigate with visible draft state, standard composer focus behavior, and Shift+Enter discoverability.
- **Lifecycle confusion**: users may not understand why Request changes resumes the same stage. Mitigate with explicit copy that the card stays in its workflow stage and begins a new attempt.

## Implementation Notes

- Product copy must distinguish selecting Request changes, editing its draft, sending it, and beginning the next attempt.
- Content-free measurement may record inbox group selection, review availability, draft abandonment, successful change-request dispatch, and stale-review rejection. It must not record card titles, prompts, code, diff content, paths, or repository names.
