# ADR-003: Derive supervision projections and keep navigation state renderer-local

## Status

Accepted

## Date

2026-07-26

## Context

The Work Inbox needs one authoritative cross-project view of repositories, boards, cards, attempts, attention, review availability, and deterministic priority. The existing host snapshot already contains the durable entities, while the current workspace projection exposes only board metadata. The renderer also needs to preserve selected board, selected card, workbench mode, prior route, and responsive focus without turning those presentation choices into workflow state.

## Decision

Add a typed `SupervisionProjection` to the existing desktop RPC contract. The host derives it on demand from the authoritative persistence snapshot and review-evidence availability. The derivation is a pure function with stable ordering:

1. `needs_attention`
2. `ready_for_review`
3. failed
4. running
5. other settled work

No new materialized supervision table is introduced. Existing projection-commit notifications invalidate the renderer query, which refetches the complete supervision projection by revision.

The renderer's existing desktop view store owns only ephemeral navigation and layout state:

- active repository and board;
- selected card and attempt;
- workbench open/closed and desktop/narrow presentation;
- prior route for Settings return;
- board scroll/focus restoration anchors.

Card drafts remain locally persisted by card identity. Workflow entities, statuses, counts, review availability, and ordering inputs remain host-authoritative. Renderer state must reference durable identities rather than copy workflow records.

## Alternatives Considered

### Alternative 1: Persist a materialized supervision projection

- **Description**: Add tables updated transactionally with every card, attempt, attention, and review event.
- **Pros**: Fast reads at large scale and direct indexed queries.
- **Cons**: Introduces another projection lifecycle, migration surface, and rebuild contract before scale requires it.
- **Why rejected**: The current authoritative snapshot can derive the V1 projection deterministically with less state and fewer failure modes.

### Alternative 2: Aggregate per-board queries in the renderer

- **Description**: Fetch each board and calculate counts and priority in React state.
- **Pros**: Minimal host changes.
- **Cons**: Duplicates workflow semantics in the renderer, causes N+1 reads, and risks inconsistent ordering across surfaces.
- **Why rejected**: It violates the host-owned projection boundary and cannot provide one trustworthy Work Inbox.

### Alternative 3: Persist navigation in the host

- **Description**: Store selected board, card, route, workbench layout, and drafts with workflow data.
- **Pros**: Restores the exact interface after restart.
- **Cons**: Mixes presentation state with durable workflow truth and adds writes for incidental navigation.
- **Why rejected**: The PRD requires restoration during navigation and layout changes, not durable server-side UI sessions.

## Consequences

### Positive

- Work Inbox state has one authoritative derivation.
- No duplicate materialized projection needs migration or rebuild support.
- Renderer navigation remains fast and independent of host writes.
- Existing revision invalidation can refresh the new projection.

### Negative

- Every supervision query scans and sorts the current snapshot.
- Navigation state does not restore across a full application restart, except card drafts.
- A future scale threshold may require materialization.

### Risks

- Large snapshots could make derivation expensive. Add deterministic performance fixtures and materialize only after measured need.
- Renderer references can become stale after card deletion or movement. Clear invalid identities when a refreshed projection no longer contains them.
- Local drafts can outlive a card. Remove or quarantine orphaned drafts during card selection.

## Implementation Notes

- Extend existing shared RPC types and board/workspace query wiring instead of creating a new package.
- Keep sort keys explicit and fully deterministic, including tie breakers by repository, board, card update time, and stable identity.
- Do not place prompt, transcript, diff, or raw path content in content-free instrumentation.
