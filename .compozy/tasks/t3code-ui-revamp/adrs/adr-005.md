# ADR-005: Treat prompt submission as authorization for safe-boundary dispatch

## Status

Accepted

## Date

2026-07-26

## Context

The current follow-up queue promotes a settled FIFO head into an awaiting-confirmation state and requires a second confirmation before dispatch. The approved product contract removes that extra step: Enter sends directly, while V1 still does not claim universal mid-turn injection.

The host must preserve ordering, idempotency, attempt generation fencing, crash safety, and explicit user authorization without silently interrupting the active turn.

## Decision

Replace the confirmation-oriented follow-up command surface with one `submitCardPrompt` command.

The renderer sends one idempotent submission containing submission identity, card identity/version, optional active attempt identity/generation, source (`initial`, `composer`, or `request_changes`), text, and review evidence identity when required.

The host resolves the card state:

- active attempt: persist the submission as an authorized FIFO item and dispatch it automatically when the current turn reaches a safe settled boundary;
- settled non-review card: start a new attempt immediately;
- `ready_for_review` with `request_changes`: revalidate evidence, record the change-request disposition, and start a new attempt on the same card and stage;
- `needs_attention`: reject ordinary submission until the blocker is resolved;
- stale identity or generation: return a typed conflict without dispatch.

The queue no longer has `awaiting_confirmation` or `confirmed` states. Its durable item states are `queued`, `dispatching`, `dispatched`, `removed`, and `interrupted`.

The host persists `dispatching` before calling the agent. A successful call records `dispatched`. If the process loses certainty while `dispatching`, recovery marks the item `interrupted` and surfaces it for explicit retry or editing; it never silently resends an ambiguous prompt.

Selecting Request changes only creates a renderer draft. The host sees no submission until the reviewer presses Enter.

## Alternatives Considered

### Alternative 1: Retain a second confirmation

- **Description**: Keep `awaiting_confirmation` and require a later confirm command.
- **Pros**: Strong explicitness before dispatch after a turn settles.
- **Cons**: Contradicts direct Enter behavior and adds a redundant interaction after the user already authorized the text.
- **Why rejected**: Pressing Enter is the authorization event.

### Alternative 2: Interrupt the active turn

- **Description**: Cancel or steer the current turn immediately when Enter is pressed.
- **Pros**: Lowest apparent latency.
- **Cons**: Provider capability varies and interruption can lose or duplicate work.
- **Why rejected**: V1 guarantees safe-boundary FIFO delivery, not universal live injection.

### Alternative 3: Disable the composer while active

- **Description**: Accept input only after the active turn settles.
- **Pros**: Simplest dispatch model.
- **Cons**: Prevents the user from recording direction while context is fresh.
- **Why rejected**: A persistent composer must accept explicitly submitted follow-ups during active work.

## Consequences

### Positive

- The visible Enter behavior matches durable host semantics.
- FIFO order and generation fencing remain authoritative.
- No prompt dispatches without an explicit submission.
- Crash ambiguity fails visibly instead of duplicating a prompt.

### Negative

- Existing confirmation RPC, queue states, tests, and UI must be migrated.
- An active-turn submission may wait before dispatch.
- Interrupted dispatches require an explicit recovery experience.

### Risks

- Queue migration can strand old awaiting-confirmation items. Convert them to authorized queued items only when an explicit prior submission is recorded; otherwise surface them as interrupted.
- A settled callback can race with removal. Fence every transition with queue version and submission identity.
- Request-changes admission spans evidence validation and attempt startup. Commit the disposition only through the coordinator path that admits the replacement attempt.

## Implementation Notes

- Keep command callbacks rejection-safe so failures never escape into React.
- Remove `confirmQueuedFollowUp` from shared RPC and renderer clients after the migration bridge is no longer needed.
- Preserve content-free diagnostics using fixed outcomes only.
