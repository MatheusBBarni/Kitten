# ADR-006: Require packaged native lifecycle-matrix verification

## Status

Accepted

## Date

2026-07-26

## Context

Automated component and contract tests can prove state transitions, keyboard handling, RPC bounds, and accessibility attributes, but they cannot prove that the packaged Electrobun application matches the intended T3 Code-inspired hierarchy or remains usable across real desktop sizes and lifecycle states.

Past desktop work has produced green automated gates without obtaining valid native visual evidence. This revamp changes the application shell, density, navigation, workbench, transcript, composer, diff, Settings, and responsive behavior; visual proof is therefore part of correctness.

## Decision

Completion requires both:

1. automated type, unit, integration, coverage, migration, RPC, accessibility, and deterministic evidence tests; and
2. a real packaged Electrobun capture reviewed against a versioned lifecycle-state matrix.

The native matrix includes at minimum:

- empty and populated Work Inbox;
- `needs_attention`, `ready_for_review`, failed, running, and settled groups;
- board with workbench closed and open;
- latest conversation with grouped tool activity;
- persistent composer idle, queued, blocked, request-changes draft, and interrupted states;
- review manifest, text diff, binary entry, too-large entry, stale evidence, Approve, and Request changes;
- Settings entry and return-context restoration;
- keyboard focus states;
- wide, medium, and narrow window layouts;
- light, dark, and reduced-motion preferences where supported.

Reference captures from `/Users/matheusbbarni/projects/t3code` guide hierarchy and visual language, but Kitten's semantic state labels and Kanban model remain the acceptance authority.

Browser-renderer screenshots may accelerate iteration but do not satisfy the native gate. If native capture is unavailable, the implementation remains partial unless the user explicitly waives that gate.

## Alternatives Considered

### Alternative 1: Browser-renderer screenshots

- **Description**: Validate visual changes in a browser using the renderer bundle.
- **Pros**: Fast, scriptable, and easy to compare.
- **Cons**: Does not prove packaged window behavior, native sizing, fonts, focus, or Electrobun integration.
- **Why rejected**: It is useful evidence but not equivalent to the shipped surface.

### Alternative 2: Automated tests only

- **Description**: Rely on components, snapshots, accessibility tests, and RPC contracts.
- **Pros**: Deterministic and CI-friendly.
- **Cons**: Cannot judge hierarchy, clipping, density, focus visibility, or overall reference fidelity.
- **Why rejected**: The PRD makes the visual and usage model part of the feature.

## Consequences

### Positive

- Completion claims include evidence from the actual shipped surface.
- The matrix prevents attractive happy-path screenshots from hiding lifecycle regressions.
- Visual acceptance remains separate from automated functional evidence.

### Negative

- Native verification takes additional time and environment support.
- State fixtures and reference captures require maintenance.
- A technically green change can remain incomplete when native evidence is unavailable.

### Risks

- Native automation can be flaky. Use deterministic fixtures, stable window sizes, and bounded retries while retaining the requirement for a real capture.
- Reference fidelity can become subjective. Record specific hierarchy, spacing, focus, status, and responsive acceptance notes beside each capture.
- The matrix can grow without bound. Keep V1 limited to states that change layout, action availability, or trust.

## Implementation Notes

- Store matrix definitions and expected capture metadata with desktop tests or visual fixtures in the existing package.
- Do not treat screenshot pixel equality as the sole gate; combine capture review with semantic state assertions.
- Stop packaged app and capture processes after verification.
